خطة إنجاز تطبيق VEILO

خطة تنفيذ تقنية مفصلة وفق PRD V1
الإصدار: 1.0   |   آخر تحديث: 10 سبتمبر 2026

طريقة قراءة الوثيقة: الرمز ☑ يعني أن العمل موجود في الكود الحالي، والرمز ☐ يعني أنه لم يُنفذ بعد أو يحتاج تحققاً إنتاجياً. لا يعني وجود الكود أن الاختبارات التشغيلية قد نجحت؛ يجب تشغيل الاختبارات قبل اعتماد أي بند نهائياً.

1. الحالة الحالية والقرار الهندسي

المشروع مبني على Laravel وPostgreSQL وبنية Modular Monolith مع فصل Domain Actions وHTTP Controllers. الأولوية الحالية هي تثبيت Messaging Core واختبارها قبل إضافة WebSocket أو واجهة المستخدم.

المجالالحالةالملاحظات
الحسابات والمصادقة☑ منفذ جزئياًRegistration، JWT، Refresh Rotation، Recovery، Device Secret، Logout.
توثيق API☑ منفذPostman Collection وEnvironment وREADME.
Messaging Core☑ منفذ كنسخة أوليةConversations، Messages، Blocks، Encryption، Idempotency، Cursor Pagination.
اختبارات Messaging☑ مكتوبة / ☐ منفذة فعلياًاختبارات PHPUnit موجودة، لكن تشغيلها يحتاج تثبيت vendor وبيئة قاعدة بيانات مناسبة.
WebSocket وReverb☐ غير منفذيأتي بعد تثبيت REST Messaging.
Notifications وSearch☐ غير منفذيُنفذان عبر Queue وOutbox بعد الرسائل.

4. المرحلة الثالثة: المصادقة والجلسات والأجهزة

الحالةالمتطلبمعيار القبول
☑Access JWT قصير العمرمدة تقريباً 15 دقيقة مع توقيع مستقل عن APP_KEY.
☑Refresh Token Rotationالتوكن opaque وهاشه فقط في قاعدة البيانات، والتوكن القديم لا يعاد استخدامه.
☑Reuse Detectionإلغاء عائلة التوكن المتأثرة وتسجيل Security Event دون إلغاء جلسات المستخدم الأخرى.
☑Logout current/allإبطال الجهاز وAccess JWT فوراً عبر revoked_at، مع الحفاظ على primary designation.
☑Device Secret Recoveryتوليد secret عشوائي، تخزين hash، وإصدار جلسة جديدة بعد التحقق.
☐JWT issuer وaudience validationرفض JWT الموقع صحيحاً لكنه صادر لخدمة أو بيئة أخرى.
☐تدوير Device Secretإبطال السر السابق وإصدار سر جديد مع Security Event.
☐إدارة Primary Deviceترقية جهاز أو إزالة primary فقط من الجهاز primary الحالي، مع قيد قاعدة البيانات.
☐اختبار التزامن للمصادقةاختبار refresh متزامن، logout أثناء refresh، وrestore أثناء revoke.

5. المرحلة الرابعة: Messaging Core

5.1 قاعدة البيانات والنماذج

الحالةالبندالتفاصيل
☑Conversationsزوج canonical بين user_low_id وuser_high_id مع unique constraint وcheck للترتيب.
☑Messagessequence_no، reply_to_message_id، client_message_id، timestamps، soft delete.
☑User Blocksقيد فريد على blocker_id وblocked_id وحظر directional.
☑الفهارسفهارس المستخدمين والمحادثات والرسائل النشطة وidempotency في PostgreSQL.

5.2 الرسائل والحماية

الحالةالبندمعيار القبول
☑تشفير at-restلا يُحفظ النص الصريح؛ يستخدم MessageCipher ومفتاحاً مستقلاً.
☑Key rotationدعم المفتاح الحالي والمفاتيح السابقة حسب encryption_key_version.
☑Idempotencyإعادة client_message_id تعيد الرسالة السابقة ولا تنشئ صفاً جديداً.
☑Reply validationرفض reply إذا كان الهدف في محادثة مختلفة.
☑Authorizationالمشارك فقط يقرأ أو يرسل، والمرسل فقط يعدل أو يحذف.
☑Cursor paginationترتيب ثابت عبر sequence_no وعدم استخدام offset.
☐Delivered stateتحديث delivered عند وصول الرسالة إلى جهاز مستلم واحد على الأقل.
☐Read stateحالة قراءة على مستوى الحساب، متزامنة بين الأجهزة.
☐Conversation listing محسّنإرجاع آخر رسالة وحالة القراءة لكل محادثة بعد اكتمال message states.

13. بوابة قبول الإصدار V1

  • ☐ جميع متطلبات P0 مغطاة بالكود واختبارات ناجحة.
  • ☐ لا توجد نتائج High أو Critical في security review.
  • ☐ كل migrations اختُبرت على نسخة PostgreSQL نظيفة ونسخة تحتوي بيانات.
  • ☐ لا توجد أسرار أو رسائل أو توكنات في logs أو Postman committed variables.
  • ☐ تم اختبار logout وrefresh reuse وrecovery وDevice Secret على أكثر من جهاز.
  • ☐ تم اختبار block وprivacy وauthorization باستخدام مستخدمين مختلفين.
  • ☐ تم اختبار WebSocket expiration وreconnect بعد تجديد JWT.
  • ☐ تم تشغيل load test وقياس زمن الاستجابة ومعدل الأخطاء.
  • ☐ توجد خطة rollback وbackup وincident response قبل النشر.
ملاحظة إنتاجية: لا تعتبر البنود التي تحمل ☑ مكتملة إنتاجياً إلا بعد تشغيل الاختبارات فعلياً على PostgreSQL وإغلاق متطلبات التشفير والمراقبة والنسخ الاحتياطي. الكود الحالي يغطي أساس Messaging Core والمصادقة، بينما Realtime وNotifications وSearch وDelivered/Read ما زالت مراحل لاحقة.
